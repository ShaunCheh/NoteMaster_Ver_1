# 五线谱 JSON 驱动分阶段计划

## 目标

- 基于当前 `Shared/Staff` 架构，把五线谱从“只画谱号”升级为“由结构化乐谱数据驱动绘制”。
- 首批验收范围限定为：`clef = treble / bass`、单声部顺序音符、`pitch + duration`、双平台同源渲染。
- 首批不把 demo 数据接入设置面板，也不做外部文件读取；数据先由代码中的 JSON 风格 fixture 提供。

## 关键现状

- 当前共享状态入口是 [NoteMaster_Ver_1/Shared/Controls/StaffDisplayState.swift](NoteMaster_Ver_1/Shared/Controls/StaffDisplayState.swift)，它只持有 `StaffConfiguration`，并从配置派生 `sceneProvider`。
- 当前场景生成器是 [NoteMaster_Ver_1/Shared/Staff/StaffSceneProvider.swift](NoteMaster_Ver_1/Shared/Staff/StaffSceneProvider.swift)，它只生成 clef glyph。
- 当前渲染场景是 [NoteMaster_Ver_1/Shared/Staff/StaffScene.swift](NoteMaster_Ver_1/Shared/Staff/StaffScene.swift)，已具备 `glyph + lineSegments` 基础，但 `StaffGlyphSymbolID` 和 renderer 仍明显偏 clef 专用。
- 当前可复用的音高模型在 [NoteMaster_Ver_1/Shared/Fretboard/NotePitch.swift](NoteMaster_Ver_1/Shared/Fretboard/NotePitch.swift)，其语义上不依赖指板几何，可以先直接复用。
- 当前最值得借鉴的模式是 [NoteMaster_Ver_1/Shared/Fretboard/FretboardSceneBuilder.swift](NoteMaster_Ver_1/Shared/Fretboard/FretboardSceneBuilder.swift) 和 [NoteMaster_Ver_1/Shared/Fretboard/FretboardValidation.swift](NoteMaster_Ver_1/Shared/Fretboard/FretboardValidation.swift)。

## 目标链路

```mermaid
flowchart LR
jsonFixture["代码里的 JSON Fixture"] --> scoreDto["StaffScoreDTO"]
scoreDto --> staffScore["StaffScore"]
staffScore --> sceneBuilder["StaffSceneBuilder"]
sceneBuilder --> staffScene["StaffScene"]
staffScene --> staffLayer["StaffRootLayer/StaffGlyphLayer"]
```



## 阶段 1：建立乐谱领域输入层

涉及文件：新增 [NoteMaster_Ver_1/Shared/Staff/StaffScore.swift](NoteMaster_Ver_1/Shared/Staff/StaffScore.swift)、[NoteMaster_Ver_1/Shared/Staff/StaffScoreDecoding.swift](NoteMaster_Ver_1/Shared/Staff/StaffScoreDecoding.swift)，复用 [NoteMaster_Ver_1/Shared/Fretboard/NotePitch.swift](NoteMaster_Ver_1/Shared/Fretboard/NotePitch.swift)。

本阶段目标：把“代码里的 JSON 风格配置”收口到共享层领域模型，不让控制器或 renderer 直接处理字符串。

具体动作：

- 定义 `StaffScore`、`StaffScoreNote`、`StaffNoteDuration`。
- 让 DTO 层负责把 `"treble" / "bass"`、`"g4"`、`"四分"` 这类字符串归一化成共享域模型。
- 内部统一使用英文枚举值，例如 `whole / half / quarter`；中文时值仅在解码边界兼容。
- 直接复用现有 `NotePitch`，首批先不做物理迁移，避免无关的工程文件扰动；等 Staff 与 Fretboard 都稳定依赖后，再单独评估是否上提到更通用目录。
- 预留 DTO 到领域模型的失败路径，确保非法音高或非法时值能在共享层被拒绝。

本阶段验收：

- 能在共享层表达一份 `clef + notes` 的 `StaffScore`。
- 控制器层只拿到强类型 `StaffScore`，不碰音高和时值字符串解析。

## 阶段 2：把 StaffScene 从 clef-only 扩成通用记谱场景

涉及文件：修改 [NoteMaster_Ver_1/Shared/Staff/StaffScene.swift](NoteMaster_Ver_1/Shared/Staff/StaffScene.swift)、[NoteMaster_Ver_1/Shared/Staff/MusicGlyph.swift](NoteMaster_Ver_1/Shared/Staff/MusicGlyph.swift)、[NoteMaster_Ver_1/Shared/Staff/CoreTextMusicGlyphRenderer.swift](NoteMaster_Ver_1/Shared/Staff/CoreTextMusicGlyphRenderer.swift)。

本阶段目标：让 scene 能同时承载 clef、notehead、符干、加线，而不是继续把所有图元硬塞进 clef 语义里。

具体动作：

- 扩展 `StaffGlyphSymbolID`，加入 notehead 相关符号，必要时预留 accidental 符号位。
- 保留现有 `lineSegments` 用于五线谱本体，同时新增一类附加线段语义，专门表达符干和加线，避免把它们伪装成 staff line。
- 让 `CoreTextMusicGlyphRenderer` 拆开“clef 专用锚点/裁切逻辑”和“普通 frame glyph 绘制逻辑”，不要再通过 `symbolID.clef` 反推所有 glyph 行为。
- 保持 `StaffSceneProvider` 仍可存在，但退化为过渡适配层，不再承载核心布局算法。

本阶段验收：

- `StaffScene` 已能无歧义表达 clef、notehead、stem、ledger line。
- renderer 可以正确绘制 frame-based note glyph，而不会误走 clef 的 trim/anchor 逻辑。

## 阶段 3：新增 StaffSceneBuilder，收口音高到谱面位置的核心算法

涉及文件：新增 [NoteMaster_Ver_1/Shared/Staff/StaffSceneBuilder.swift](NoteMaster_Ver_1/Shared/Staff/StaffSceneBuilder.swift)、[NoteMaster_Ver_1/Shared/Staff/StaffPitchLayout.swift](NoteMaster_Ver_1/Shared/Staff/StaffPitchLayout.swift)，并修改 [NoteMaster_Ver_1/Shared/Staff/StaffSceneProvider.swift](NoteMaster_Ver_1/Shared/Staff/StaffSceneProvider.swift)、[NoteMaster_Ver_1/Shared/Staff/StaffGeometry.swift](NoteMaster_Ver_1/Shared/Staff/StaffGeometry.swift)。

本阶段目标：建立真正的 `StaffScore + StaffGeometry -> StaffScene` builder，彻底把“乐谱语义”与“绘制实现”分开。

具体动作：

- 参照 `FretboardSceneBuilder` 的模式，让 `StaffSceneBuilder` 成为共享层唯一的谱面构建入口。
- 在 `StaffPitchLayout` 中实现 treble / bass 下的音高到谱线位置映射。
- 统一计算 note 的横向分布、notehead frame、符干方向、符干长度、超出五线的加线位置。
- 首批把时值只用于符形选择和符干规则，不做复杂节奏比例排版；这样能先把“数据驱动渲染”从根上打通，再为后续拍号、小节和 spacing 策略留口。
- 把 `StaffSceneProvider.makeScene(geometry:)` 改成轻量封装，内部转调 `StaffSceneBuilder`。

本阶段验收：

- 同一份 `StaffScore` 在 treble / bass 下都能生成正确的 note 垂直位置。
- 四分、二分、全分音符在 scene 层有明确差异。
- 视图缩放或 resize 时，音符布局跟随 `StaffGeometry` 稳定变化。

## 阶段 4：把 Score 接入共享状态和双平台控制器

涉及文件：修改 [NoteMaster_Ver_1/Shared/Controls/StaffDisplayState.swift](NoteMaster_Ver_1/Shared/Controls/StaffDisplayState.swift)、[NoteMaster_Ver_1/Platform/iOS/iOSViewController.swift](NoteMaster_Ver_1/Platform/iOS/iOSViewController.swift)、[NoteMaster_Ver_1/Platform/macOS/macOSViewController.swift](NoteMaster_Ver_1/Platform/macOS/macOSViewController.swift)，按需要少量调整 [NoteMaster_Ver_1/Platform/iOS/iOSStaffView.swift](NoteMaster_Ver_1/Platform/iOS/iOSStaffView.swift) 和 [NoteMaster_Ver_1/Platform/macOS/macOSStaffView.swift](NoteMaster_Ver_1/Platform/macOS/macOSStaffView.swift)。

本阶段目标：让双平台都通过共享状态消费同一份 demo score，而不是各自散落一份绘制逻辑。

具体动作：

- 在 `StaffDisplayState` 中增加 `score` 或等价的内容输入字段。
- 继续让 `StaffDisplayState` 作为 staff 真相来源，避免控制器直接操作 `sceneProvider` 细节。
- 新增共享 demo fixture 工厂，例如 `StaffScoreFixtures`，由共享层提供默认示例谱面。
- iOS/macOS 控制器只负责在启动时注入同一份 fixture，不把 fixture 选择接进设置面板。
- 保持现有 settings 架构不变，除非后续明确要做“切换 demo 谱例”的 UI。

本阶段验收：

- iOS 和 macOS 显示同一份共享 score。
- 设置面板现有 clef/调试项不回归，不需要因为 score 接入而被重写。

## 阶段 5：补共享层验证器和回归护栏

涉及文件：新增 [NoteMaster_Ver_1/Shared/Staff/StaffValidation.swift](NoteMaster_Ver_1/Shared/Staff/StaffValidation.swift)，参考 [NoteMaster_Ver_1/Shared/Fretboard/FretboardValidation.swift](NoteMaster_Ver_1/Shared/Fretboard/FretboardValidation.swift)。

本阶段目标：在没有 `Tests` target 的前提下，为 staff 新能力建立可重复运行的 scene fixture 验证。

具体动作：

- 定义 treble / bass、多组典型音高、不同时值的 fixture 矩阵。
- 自动校验 `drawingRect` 非空、glyph 数量匹配、notehead 未越界、ledger line 在高低音边界正确出现。
- 校验 treble 与 bass 下的音高映射顺序，避免谱号切换后位置错行。
- 输出统一 `debugSummary()`，在 debug 环境下支持启动期自动报告或断言。
- 补一份双平台手工检查清单，覆盖 resize、clef 切换、同一 fixture 的平台一致性。

本阶段验收：

- 新功能具备可重复跑的共享层 fixture 校验，不依赖脆弱的 UI 快照。
- 后续继续扩休止符、升降记号、和弦时，有稳定护栏可复用。

## 建议的实施顺序

1. 先完成领域模型和 DTO 归一化，再动 scene；不要反过来让 renderer 直接理解 JSON。
2. 再完成 `StaffScene` 通用化和 `StaffSceneBuilder`，让音高布局逻辑落在共享层。
3. 最后再接入 `StaffDisplayState` 与双平台控制器，并补验证器。

## 风险与控制点

- 最大风险不在 UI，而在 renderer 仍然把所有 glyph 当 clef 处理，所以阶段 2 必须先拆 clef 专用逻辑。
- 时值如果一开始就绑定复杂节奏间距，会把范围迅速拉大；首批先让时值决定符形，不做完整 engraving spacing，是更稳的切法。
- `NotePitch` 的物理目录迁移不是首批阻塞项；首批先复用语义，再看是否值得在后续单独做结构整理。
