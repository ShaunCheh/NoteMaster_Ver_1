# 竖向指板局部横滚方案

## 目标与约束

- 采用你确认的 `方案2`，但收敛为“仅指板区域横向滚动，五线谱保持当前页面宽度”。
- 保留 [NoteMaster_Ver_1/Shared/Controls/FretboardDisplayState.swift](NoteMaster_Ver_1/Shared/Controls/FretboardDisplayState.swift) 中 `verticalHostHeightRatio` 的语义：它继续表达“指板宿主高度占安全区高度的比例”。
- 保持 [NoteMaster_Ver_1/Platform/iOS/iOSViewController.swift](NoteMaster_Ver_1/Platform/iOS/iOSViewController.swift) / [NoteMaster_Ver_1/Platform/macOS/macOSViewController.swift](NoteMaster_Ver_1/Platform/macOS/macOSViewController.swift) 的页面主滚动仍然以纵向为主，不让 staff 跟着横向变宽。
- 根因要修在“尺寸真相链路”上：当前外层把 `fretboardView` 高度拉满，而 shared 竖向几何又会在宽度不足时把整图按宽度缩短并垂直居中；本轮要把“竖向内容宽度”显式落成横向 scroll 的内容宽度真相。

## 当前关键链路

- [NoteMaster_Ver_1/Platform/iOS/iOSViewController.swift](NoteMaster_Ver_1/Platform/iOS/iOSViewController.swift) 与 [NoteMaster_Ver_1/Platform/macOS/macOSViewController.swift](NoteMaster_Ver_1/Platform/macOS/macOSViewController.swift) 目前都把 `contentView` 宽度锁在 viewport 宽度，并在竖向模式下使用 `fretboardView.top/bottom == fretboardHostView` + `fretboardView.width <= fretboardHostView.width`。
- [NoteMaster_Ver_1/Shared/Fretboard/FretboardConfiguration.swift](NoteMaster_Ver_1/Shared/Fretboard/FretboardConfiguration.swift) 已具备 `resolvedWidth(forAvailableHeight:)` / `verticalTotalWidth(...)` 这条“给定高度算整把竖向指板理论宽度”的共享能力，可直接复用。
- [NoteMaster_Ver_1/Shared/Fretboard/VerticalFretboardGeometryStrategy.swift](NoteMaster_Ver_1/Shared/Fretboard/VerticalFretboardGeometryStrategy.swift) 当前 `makeDrawingRect(...)` 采用“整图塞进 `bounds`”策略；只要 `bounds.width` 仍被限制在 host 宽度内，就会继续出现竖向 letterbox。

```mermaid
flowchart LR
    slider["高度滑块"] --> state["共享显示状态"]
    state --> host["指板宿主高度"]
    host --> contentWidth["竖向内容宽度"]
    contentWidth --> innerScroll["指板局部横向滚动"]
    innerScroll --> fretboardView["指板内容视图"]
    fretboardView --> scene["竖向几何场景"]
```



## 分阶段计划

### 阶段 1：重构 shared 尺寸契约，显式区分“视口高度”与“竖向内容宽度”

- 在 [NoteMaster_Ver_1/Shared/Fretboard/FretboardConfiguration.swift](NoteMaster_Ver_1/Shared/Fretboard/FretboardConfiguration.swift) 补一组面向竖向滚动场景的显式 API，例如“给定视口高度时的竖向内容宽度 / 内容总尺寸”。
- 复用现有 `verticalWidthToHeightMultiplier`、`verticalTotalWidth(...)` 等比例真相，不推翻 cell 长宽比链路。
- 明确约定：shared 层输出的是“整把竖向指板内容需要的宽度”，平台层再决定是直接显示还是放入横向 scroll。
- 保持 [NoteMaster_Ver_1/Shared/Controls/FretboardDisplayState.swift](NoteMaster_Ver_1/Shared/Controls/FretboardDisplayState.swift) 不新增新的页面高度状态，避免把 `Height` 滑块语义搅乱。

### 阶段 2：改造平台 `FretboardView` 的竖向尺寸出口

- 在 [NoteMaster_Ver_1/Platform/iOS/iOSFretboardView.swift](NoteMaster_Ver_1/Platform/iOS/iOSFretboardView.swift) 与 [NoteMaster_Ver_1/Platform/macOS/macOSFretboardView.swift](NoteMaster_Ver_1/Platform/macOS/macOSFretboardView.swift) 增加“竖向内容宽度”出口，让 view 可以在固定高度下撑出整把指板所需宽度，而不是继续被 host 宽度上限卡死。
- 让当前绿色边界继续画在 `fretboardView` 自己的 `bounds` 上，这样进入局部横滚后，绿色边界就代表真实指板内容矩形，而不是外层 viewport。
- 保留横向模式现有 intrinsic size 和约束行为，避免回归。

### 阶段 3：iOS 端引入“指板局部横向滚动”容器

- 在 [NoteMaster_Ver_1/Platform/iOS/iOSViewController.swift](NoteMaster_Ver_1/Platform/iOS/iOSViewController.swift) 的 `fretboardHostView` 内新增专用 `UIScrollView`，只承载竖向模式下的 `fretboardView`。
- 保留外层页面 `scrollView` 只纵向滚动、`contentView.width == frameLayoutGuide.width` 的现有约束，使 `staffView` 仍然锁定页面宽度。
- 将现有竖向模式约束从“`fretboardView.width <= fretboardHostView.width`”改成“viewport 贴满 host，`fretboardView.width == shared 计算出的内容宽度`”。
- 单独处理 iOS 嵌套滚动细节：横向指板 scroll 与外层纵向页面 scroll 的手势边界、bounce 与指示器策略。

### 阶段 4：macOS 端镜像局部横向滚动容器

- 在 [NoteMaster_Ver_1/Platform/macOS/macOSViewController.swift](NoteMaster_Ver_1/Platform/macOS/macOSViewController.swift) 对称引入 `NSScrollView` + `documentView` 结构，承载竖向模式下的 `macOSFretboardView`。
- 保持 staff 继续跟随页面 viewport 宽度，不参与横向扩展。
- 把当前竖向约束同样从“宽度不超过 host”替换成“内容宽度由 shared 尺寸真相驱动”。
- 联调 trackpad / 鼠标滚轮行为，确保横向滚动不破坏窗口已有纵向滚动体验。

### 阶段 5：校正 shared 竖向几何，使内容优先吃满高度

- 在 [NoteMaster_Ver_1/Shared/Fretboard/VerticalFretboardGeometryStrategy.swift](NoteMaster_Ver_1/Shared/Fretboard/VerticalFretboardGeometryStrategy.swift) 审核 `makeDrawingRect(...)` 的装箱逻辑，确保当 `bounds.width` 已经是“整把指板内容宽度”时，几何结果稳定走“高度吃满”分支，而不是继续出现垂直居中式的 letterbox。
- 保持 `cellWidthToHeightRatio`、marker、label anchor、hit-test 映射不变，避免再次打破你前面已经修好的竖向/横向 cell 比例一致性。
- 若完成前述宽度链路后仍残留少量上下空白，再单独评估 [NoteMaster_Ver_1/Shared/Fretboard/FretboardConfiguration.swift](NoteMaster_Ver_1/Shared/Fretboard/FretboardConfiguration.swift) 中 `verticalInsetRatio` 是否需要做模式化收紧；这一步只作为二次清理，不和滚动根因修复混在一起。

### 阶段 6：Settings 文案与联调验证

- 默认不改 [NoteMaster_Ver_1/Shared/Controls/SettingsPanelModel.swift](NoteMaster_Ver_1/Shared/Controls/SettingsPanelModel.swift) / [NoteMaster_Ver_1/Shared/Controls/SettingsPanelSnapshotBuilder.swift](NoteMaster_Ver_1/Shared/Controls/SettingsPanelSnapshotBuilder.swift) 的结构，因为 `Height` 滑块状态语义不变。
- 如果联调后需要减少误解，再只更新 `Height` 的标题 / accessibility 文案，说明“竖向模式下增大高度可能带来横向滚动”。
- 回归场景：
  - 竖向模式下 `Height` 最小值 / 最大值。
  - `guitar6` / `bass4` / `bass5` 不同弦数。
  - iOS 旋转、macOS 窗口 resize。
  - `horizontal <-> vertical` 切换时约束切换是否稳定。
  - 绿色组件边界是否与竖向指板内容高度一致。
  - 指板命中测试、marker、音名标签位置是否保持正确。

## 交付标准

- 竖向模式下，`fretboardView` 的绿色边界与指板内容高度对齐，不再出现“大高度 host + 窄宽度内容被垂直居中”的上大下大空白。
- staff 继续占满页面宽度，不参与横向滚动。
- `Height` 滑块仍控制页面中指板区域的高度比例，但在竖向模式下会通过局部横向滚动消化新增内容宽度，而不是继续压缩内容高度。
